# PEOPLEOS — HR SaaS PLATFORM

Você é o principal engenheiro de software responsável por projetar e implementar um SaaS completo de gestão de pessoas inspirado em plataformas como Buk.

O objetivo NÃO é copiar código, marca, identidade visual ou conteúdo proprietário do Buk.

Queremos construir um produto original, chamado provisoriamente de **PeopleOS**, utilizando conceitos comuns de sistemas modernos de HR Tech.

---

# 1. OBJETIVO DO PRODUTO

Construir uma plataforma SaaS B2B multi-tenant para empresas gerenciarem seus colaboradores.

O sistema deverá permitir:

* cadastro e gestão de empresas
* usuários e permissões
* colaboradores
* departamentos
* cargos
* unidades/filiais
* documentos
* férias
* benefícios
* onboarding
* desligamentos
* ponto/registro de jornada
* notificações
* dashboards
* auditoria
* configurações da organização

A aplicação deve ser construída pensando desde o início como um produto SaaS real, e não apenas como um CRUD demonstrativo.

# 3. PRINCÍPIOS DE ARQUITETURA

Priorize:

* código simples
* baixo acoplamento
* alta coesão
* separação clara de responsabilidades
* tipagem forte
* segurança
* testabilidade
* escalabilidade razoável
* facilidade de manutenção

NÃO criar abstrações desnecessárias.

NÃO criar "enterprise architecture" exagerada sem necessidade.

NÃO utilizar `any`, exceto quando absolutamente inevitável e documentado.

Evite duplicação.

Não coloque regra de negócio diretamente em controllers.

Controllers devem ser responsáveis principalmente por:

1. receber request
2. validar input
3. chamar o serviço/use case
4. retornar response

A lógica de negócio deve ficar em services/use cases apropriados.

# 5. MULTI-TENANCY

Esse é um dos requisitos mais importantes.

O sistema deve ser multi-tenant desde o início.

Modelo conceitual:

```text
Organization
│
├── Users
├── Employees
├── Departments
├── Positions
├── Branches
├── Documents
├── Vacations
├── Benefits
├── Onboarding
└── AuditLogs
```

As entidades pertencentes à organização devem possuir:

```text
organizationId
```

ou uma relação equivalente.

NUNCA confiar somente no `organizationId` enviado pelo frontend.

O backend deve determinar a organização a partir do contexto autenticado do usuário.

Exemplo:

```text
JWT
 ↓
Authenticated User
 ↓
Organization Membership
 ↓
Request Context
 ↓
Service
 ↓
Database query scoped by organization
```

Sempre garantir isolamento entre tenants.

Um usuário da Organization A jamais pode acessar dados da Organization B.

Criar testes especificamente para esse cenário.

# 6. RBAC

Criar sistema de permissões.

Inicialmente teremos:

```text
SUPER_ADMIN
ORG_ADMIN
HR_MANAGER
MANAGER
EMPLOYEE
```

Permissões devem ser granulares.

Exemplos:

```text
employees:read
employees:create
employees:update
employees:delete

documents:read
documents:create
documents:delete

vacations:read
vacations:request
vacations:approve
```

Não espalhar verificações como:

```typescript
if (user.role === "ADMIN")
```

por toda a aplicação.

Criar uma abordagem centralizada de authorization/guards/decorators.
